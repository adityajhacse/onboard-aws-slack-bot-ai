EDD Platform: Workload Environment Creation Design Proposal
This document is a request for comment. It proposes a target direction for discussion and alignment; it is not a finalized implementation design or committed delivery plan.
This design describes the target flow for creating a new workload environment from Slack using a supported platform golden path. The intent is simple: the user asks once, the platform plans once, and each downstream system receives the minimum typed contract it needs to do its job.
AWS Fargate is the first golden path for this design. The architecture should not be limited to Fargate; the same control plane, inventory model, orchestration pattern, and scaffolding contract should support additional golden paths over time.
1. Scope And Goal
The goal of this design is to define the target platform flow for creating and tracking a workload environment from initial request through ready state.
The platform needs to track the full lifecycle of a workload and its associated workload environment, and maintain a workload inventory: a manifest of all resources created for that workload. The workload inventory includes the workload record, the workload environment plan, AWS accounts, account baselines, GitHub repository, HCP Terraform project and workspaces, shared account/network outputs, Vault paths, resource links, and lifecycle status.
The platform should be able to answer, at any point in time:
what workload was requested
which resources are expected to exist
which resources actually exist
manifest of resources created for the workload and links to each resource
which step is currently running or failed
which action is safe to retry
This RFC focuses on the target architecture, sequencing, implementation model, and major component responsibilities. It does not define every field-level schema, every policy rule, or every migration step required to evolve existing systems.
1.1 Personas
The design has two primary personas:
Workload User: requests a workload environment, provides business/application context, and uses the resulting repository, Terraform workspaces, account links, Vault references, and status links.
Platform Admin: operates the platform control plane, reviews workload inventory and lifecycle state, investigates failures, retries safe steps, and maintains the golden path configuration, templates, and policies.
2. Overall Design
The target architecture is a small platform control plane hosted primarily in a Core Infra AWS account. The solution is a Slack bot that receives workload details from a user, validates the workload requests via lambdas exposed via API Gateway and ultimately kicks off an AWS step function to orchestrate the many resources needed to create a workload environment. Each resource (AWS accounts, GitHub Repos etc) that needs to be created would have an associated lambda function that is responsible for the creation/configuration of the resource. Data about each workload, its associated resources and the state of workload environment provisioning is kept in a workload registry implemented in DynamoDB.

2.1 Overall Design - Workload Registry And Inventory State
The workload registry is the durable inventory for the workload lifecycle. It records the workload, the requested workload environment, the resources that should be created, the resources that were actually created, the lifecycle events, and the links back to each external system.
This should be implemented in DynamoDB because the access pattern is workload-centric and event-oriented. The platform usually needs to answer questions by workload_slug, execution ID, or idempotency key; it does not need broad relational joins across all workloads. DynamoDB also gives the platform conditional writes for safe retries, high availability, serverless scaling, and a natural place to store append-only lifecycle events alongside the current inventory view.
At a high level, the registry stores:
workload metadata: what the workload is for, who owns it, who can operate it, and who is responsible for cost
workload environment intent: selected golden path, account tiers, AWS regions, DNS choices, VPC sizing, data classification, and compliance flags
created resource inventory: AWS accounts, account baselines, GitHub repository, HCP Terraform project/workspaces, shared AFT outputs, Vault paths, final scaffold commit, and resource links
orchestration state: current step, execution status, retry count, last error, and callback correlation IDs
lifecycle history: append-only events that show how the workload moved from requested to ready or failed
2.2 Overall Design - Infra Orchestrator
The Infra Orchestrator is the lifecycle coordinator. It accepts validated workload and workload environment plans, persists the desired inventory, calls the required platform components in order, records the actual resources created, and moves the workload to ready or failed state.
The orchestrator should be implemented as an AWS Step Functions state machine. This flow is long-running, crosses several external systems, waits on asynchronous account vending, and needs explicit retry and recovery behavior. Step Functions gives the platform a durable workflow, observable execution history, built-in retry and timeout handling, and a clear place to model waits, branches, and terminal states.
The state machine should own:
accepting validated workload registration and workload environment plans as the input to the creation workflow
recording desired inventory before external side effects
creating or reserving the GitHub repository shell when downstream systems need a repository target
calling AFT, HCP Terraform, AFT output sharing, Vault, and final project scaffolding in sequence
waiting for account readiness and baseline completion
recording actual inventory as each component returns references
exposing failed steps and retry targets to the operator view
moving the workload environment to ready only after the required inventory artifacts exist and the final /infra scaffold has been committed
2.3 Overall Design - Lambda Interfaces To Existing Components
Lambda functions provide thin, typed interfaces to the components used by the workflow. They translate the orchestrator's internal plan into each component's request shape, normalize responses back into the workload inventory, and keep integration details out of the state machine definition.
The handlers below are implementation interfaces for the components covered in more detail in the component sequence section:
Slack Request Handler Lambdas: receive calls from the Slack Platform Bot through API Gateway, verify Slack requests, resolve the Slack user to an enterprise identity, route action-specific requests, return validation and inventory results to Slack, and start the state machine after validation succeeds
CreateWorkload Validation Lambda: confirms required ownership, cost center details, App 360, GUS, security, vulnerability, and approval records exist
CreateWorkloadEnvironment Validation Lambda: confirms the requested golden path, account tiers, AWS regions, sizing, and environment options are allowed
GitHub Repository Lambda: creates or reserves the workload repository shell and records repository references
AFT Lambda: submits account requests and normalizes AFT response data
AFT Readiness Lambda: receives events or polls for account readiness and updates DynamoDB
HCP Terraform Lambda: creates workload project/workspaces after account readiness
AFT Output Sharing Lambda: configures the HCP Terraform output-sharing relationship from AFT account baseline workspaces to workload workspaces
Vault Lambda: calls Vault onboarding and GitHub sync
Final Scaffold Lambda: renders the final /infra folder after account, workspace, output-sharing, and Vault references are available
The Lambda layer should not become a second implementation of AFT, GitHub, HCP Terraform, or Vault. Its job is to provide a stable interface, normalize inputs and outputs, and update the workload inventory state in DynamoDB.

2.4 Overall Design - Workload Slug And Naming Conventions
The workload slug should be determined in the workload CreateWorkload step and used as the stable namespace and unique identifier for the workload. It should be up to 8 characters, enforced as unique by the workload registry, editable by the workload requester during intake, and derived from the workload name when the requester does not provide one.
Once a workload is registered, the slug should be treated as the unique identifier that ties together and the registry record, AFT requests, AWS accounts, GitHub repository, HCP Terraform project/workspaces, Vault paths, identity groups, and standard IAM/OIDC references.
Using deterministic names reduces the amount of message passing required between components. If every component can derive the expected name from the same workload slug, account environment, and golden path configuration, then the orchestrator can pass compact intent and record discovered references instead of copying every generated value between systems.
Examples:
AFT request IDs and account names include the workload slug and account tier, for example det-<workload_slug>-dev
GitHub repositories use the workload naming convention, for example det-<workload_code>
HCP Terraform projects and workspaces include the workload slug and account tier
Vault paths include the workload slug and domain/product context
IAM roles, OIDC provider references, identity groups, variable sets, and output-sharing references use names or tags that include the workload slug where platform policy allows
When a resource has to use a shared or externally constrained name, the workload slug should still appear in tags, descriptions, metadata, or registry references. The point is not to force every system into the exact same naming format; it is to make the workload identity obvious and derivable everywhere the platform operates.
2.5 Overall Design - Code Repository Scaffolding Model
Scaffolding should turn the workload inventory into a usable repository, not ask each workload team to hand-build the connections between workload resources like AWS accounts and CI/CD pipelines. The platform should use a versioned template engine, such as Jinja, to render the repository structure for the selected golden path.
This design uses a two-phase repository model. The GitHub repository is created or reserved early so downstream systems have a stable repository target. The final /infra scaffold is rendered later, after the workload inventory contains the concrete references needed by the template: AWS account IDs, VPC and subnet IDs, DNS outputs, role ARNs, HCP Terraform workspace references, AFT output-sharing references, and Vault references.
The scaffolded /infra folder should include the static conventions that should not be rebuilt by every team:
workspace mapping for each account tier
provider and backend conventions
references to standard OIDC roles used by delivery and Terraform execution
references to shared AFT outputs for account and network facts
golden-path-specific Terraform module calls that reference approved golden modules published to the HCP Terraform private module registry, such as the first AWS Fargate golden path
The important contract is that scaffolding is golden-path aware but not Fargate-specific. A future golden path should be able to provide a new template and approved module set while using the same workload registry, orchestrator, output-sharing model, and final scaffold step.
2.4 Overall Design - Operating Principles
The design should be guided by a small set of operating principles:
Persist intent before side effects. The platform should record what it plans to create before it calls external systems.
Reconcile actual state. Each component response should update the workload inventory with the resources and references that actually exist.
Make every step idempotent. If a workload record, GitHub repo, HCP workspace, AFT request, or Vault path already exists with the expected name, owner, and workload reference, the step should treat that as success and continue.
Stop on conflicts. If an expected resource already exists with conflicting ownership or configuration, the platform should stop and make the conflict visible in status.
Keep systems of record clear. DynamoDB tracks the workload inventory and orchestration state; AFT, GitHub, HCP Terraform, and Vault remain the systems of record for the resources they own.
Store references, not secrets. The workload inventory should store links, IDs, paths, and status. It should not store secret values.

3.1 Solution Component - Slack Platform Bot
The Slack Platform Bot is the Workload User-facing entry point. It should make the workflow feel guided and simple, but it should not make infrastructure decisions.
The first action is a CreateWorkload request. The Workload User issues the request through the Slack Platform Bot with the ownership and business context for the workload. The Slack Request Handlers then invoke preflight validation to confirm the App 360 record and GUS team are valid. Once those checks pass, the workload can be registered in the DynamoDB-backed workload registry.
The second action is a CreateWorkloadEnvironment request. The Workload User provides the golden path they want to use, the AWS regions they need, the account tiers they need inside the workload environment, and general information about the initial cloud environment required to support the workload.
Slack should integrate with preflight validation through commands and modals, not by embedding validation logic in the bot. The bot collects structured input, sends the signed Slack request to the Slack Request Handlers, and displays the validation result. If validation fails, the bot shows actionable missing or invalid records. If validation succeeds, the bot shows that the request was accepted and links the user to workload status.

3.2 Solution Component - Slack Request Handlers
The Slack Request Handlers are the boundary between Slack and the platform control plane. They should be exposed through API Gateway endpoints for specific Slack-backed actions, such as workload registration, workload environment creation, status lookup, inventory lookup, and operator actions. Each endpoint can route to a dedicated Lambda handler or a shared router Lambda with action-specific handlers behind it.
The handlers receive slash command and modal submissions from the Slack Platform Bot, acknowledge Slack quickly, validate that the request really came from Slack, map the Slack user to the platform identity, and turn the user input into typed platform requests.
For create actions, the handlers should call the preflight validation Lambdas before starting any creation workflow. If validation fails, they return structured errors that the Slack Platform Bot can display in the modal or as an ephemeral message. If validation succeeds, they pass the validated plan to the Infra Orchestrator and return an accepted message with a status link.
For read and operator actions, the handlers should read from the workload registry and return a consistent inventory view: what has been provisioned, what is still in progress, what failed, and which retry or reconcile actions are available. Over time, this inventory read model could also be exposed through an MCP server so the Slack Platform Bot can answer richer operator questions about workloads, environments, accounts, repositories, Terraform workspaces, Vault paths, and lifecycle state.
The Slack Request Handlers should also support outbound Slack updates. When a request reaches a major milestone or completes, the platform should post back to the originating Slack thread or channel with the current state and the relevant resource links.

3.13 Solution Component - Final Infra Scaffolding
Final infra scaffolding is the step that makes the repository ready for the Workload User. It runs late in the flow because the template needs the concrete inventory created by earlier steps: account IDs, VPC IDs, subnet IDs, DNS outputs, role ARNs, HCP Terraform workspace references, AFT output-sharing references, and Vault references.
The scaffolding service should use a versioned template engine, such as Jinja, to render the /infra folder. The template should generate the standard Terraform structure that should not be hand-built by every team: workspace mapping for each account tier, provider conventions, backend conventions, references to the standard OIDC roles that exist in each AWS account for pipeline and Terraform execution, and references to the shared Terraform outputs published through the AFT output-sharing contract.
The template system should be golden-path aware. For the first golden path, it should scaffold the /infra frame needed for an AWS Fargate workload. Over time, the same pattern should support additional golden paths by rendering the right repository structure, workspace mapping, provider conventions, and Terraform module calls for that path. Those Terraform module calls should reference approved golden modules published to the HCP Terraform private module registry. For example, a Fargate template can call golden Fargate modules from the registry, and a future golden path can provide its own approved module set and template inputs.
